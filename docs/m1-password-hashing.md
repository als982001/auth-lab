# M1 — 비밀번호 해싱

> **한 줄 요약**: 비밀번호는 평문으로도, 빠른 해시(SHA256)로도 저장하면 안 된다. **솔트 + 의도적으로 느린 해시**가 정답이고, bcrypt가 그 둘을 한 번에 해준다.

인증에서 사고가 나면 대부분 여기서 난다. 이 프로젝트에서 가장 중요한 개념.

---

## 1. 평문 저장이 왜 안 되나

```js
users.push({ email, password: "1234" }); // ❌
```

당연해 보이지만 **왜** 안 되는지가 중요하다. DB가 털렸을 때의 피해 범위가 달라진다.

평문이면 유출 = 즉시 전 계정 장악. 그런데 더 큰 문제는 **연쇄 피해**다. 사람들은 비밀번호를 여러 서비스에 재사용한다. 이 서비스에서 샌 비밀번호로 공격자가 그 사람의 메일·은행·다른 서비스를 전부 시도한다. 이걸 **credential stuffing**이라 하고, 실제 대형 사고 대부분이 이 경로다.

> 비밀번호 저장은 "내 서비스만의 문제"가 아니다. **남의 다른 서비스 보안까지 쥐고 있는 셈이다.**

---

## 2. 해시 — 되돌릴 수 없게

해시 함수는 **단방향**이다. 평문 → 해시는 되지만, 해시 → 평문은 안 된다.

```
"1234"  →  해시함수  →  "03ac674216f3e15c..."
"1234"  →  해시함수  →  "03ac674216f3e15c..."   ← 같은 입력 = 항상 같은 출력
```

그래서 검증 방식의 발상이 바뀐다.

|     |                                                   |
| --- | ------------------------------------------------- |
| ❌  | 저장된 걸 **복호화해서 비교**한다                 |
| ✅  | 입력받은 걸 **똑같이 해싱해서 결과끼리 비교**한다 |

**서버조차 사용자의 원래 비밀번호를 모르는 상태**가 정상이다. 그래서 "비밀번호 찾기"가 아니라 "비밀번호 재설정"인 것.

---

## 3. 그런데 SHA256도 안 된다

가장 많이 틀리는 지점. "해시 썼으니 됐다"가 아니다. 이유가 **두 개**다.

### (a) 너무 빠르다

SHA256은 원래 **빠르라고 설계된** 함수다. 파일 무결성 검사용이라 GPU 기준 초당 수십억 번 계산된다.

비밀번호 저장의 요구사항은 **정반대**다. 공격자가 해시를 손에 넣었을 때 무차별 대입을 못 하게 하려면 **느려야** 한다.

|           | 정상 로그인               | 공격자 무차별 대입      |
| --------- | ------------------------- | ----------------------- |
| 빠른 해시 | 1회 × 0.000001초 = 무의미 | **초당 수십억 회 시도** |
| 느린 해시 | 1회 × 0.1초 = 체감 없음   | **초당 10회 시도**      |

**핵심은 비대칭이다.** 사용자는 로그인 시 한 번만 계산하니 0.1초가 문제되지 않는다. 공격자는 수십억 번 해야 하니 그 0.1초가 곱해져 수백 년이 된다.

### (b) 레인보우 테이블

같은 입력 → 항상 같은 출력이므로, 공격자가 **미리 계산해둘 수 있다.**

```
"1234"      → 03ac674216f3e15c...
"password"  → 5e884898da280471...
"qwerty"    → 65e84be33532fb78...
...흔한 비밀번호 수억 개를 표로 작성
```

해시를 훔치면 계산할 필요도 없이 **표에서 조회만 하면 된다.** 흔한 비밀번호는 즉시 뚫린다.

---

## 4. 솔트 — 미리 계산을 막는다

**솔트(salt)** = 유저마다 다른 랜덤 문자열. 비밀번호에 붙여서 해싱한다.

```
유저A: "1234" + "x7Kp9..." → 해시1
유저B: "1234" + "mQ2vR..." → 해시2     ← 같은 비밀번호인데 해시가 다름
```

### 솔트가 막는 것 두 가지

**1) 레인보우 테이블 무력화**
공격자가 표를 만들려면 이제 **솔트별로 따로** 만들어야 한다. 솔트가 유저마다 다르니 유저 수만큼 표가 필요해지고, 미리 계산해두는 의미가 사라진다.

**2) 비밀번호 재사용 노출 방지**
솔트가 없으면 해시 목록만 봐도 "이 두 계정은 같은 비밀번호를 쓴다"가 드러난다. 공격자에게 좋은 힌트다. 솔트가 있으면 이 정보가 새지 않는다.

### ⚠️ 솔트는 비밀이 아니다

헷갈리기 쉬운 부분. 솔트는 **해시와 함께 저장해도 되고, 그래야 한다** (로그인 시 같은 솔트로 다시 해싱해야 하므로).

목적이 **"숨기기"가 아니라 "미리 계산을 막기"** 이기 때문이다.

---

## 5. bcrypt — 솔트 + 느림을 합친 것

bcrypt는 **솔트 자동 생성 + 의도적으로 느림**을 한 번에 제공한다.

### cost factor (rounds)

핵심 파라미터. `2^cost`만큼 반복 계산한다.

| cost | 반복 횟수 | 대략 소요 |
| ---- | --------- | --------- |
| 10   | 1,024회   | ~100ms    |
| 12   | 4,096회   | ~400ms    |
| 14   | 16,384회  | ~1.5초    |

**cost를 1 올리면 2배 느려진다.**

이 구조가 좋은 이유: 하드웨어는 계속 빨라진다. 10년 뒤엔 cost 10이 너무 빨라질 텐데, 그때 **알고리즘을 바꾸지 않고 cost만 올리면** 된다. 강도를 조절 가능한 설계.

> 현재 기준 권장값: **10~12**

### 결과 포맷

```
$2b$10$N9qo8uLOickgx2ZMRZoMye  IjZAgcfl7p92ldGxad68LJZdL17lhWy
└┬┘ └┬┘ └──────── 솔트 22자 ──┘  └──────── 해시 31자 ────────┘
알고리즘 cost
```

**솔트가 결과 문자열 안에 포함되어 있다.** 그래서 솔트를 별도 컬럼에 저장할 필요가 없다 — 이 문자열 하나만 저장하면 된다. 로그인 시 bcrypt가 여기서 솔트를 알아서 꺼내 쓴다.

---

## 6. API

```js
// 해싱 — 솔트는 자동 생성
const hash = await bcrypt.hash(평문비번, 10);

// 비교 — M2에서 사용
const isMatch = await bcrypt.compare(입력한비번, 저장된해시);
```

둘 다 **Promise 반환** → 라우트 핸들러를 `async`로 만들고 `await` 사용.

### 왜 `compare`를 써야 하나

"입력값을 해싱해서 `===`로 비교하면 안 되나?" → **안 된다.** 저장된 해시에서 솔트를 꺼내 써야 하는데 직접은 못 한다. `compare`가 그 과정을 대신 해준다.

### 설치 참고

`bcrypt`는 네이티브 모듈이라 설치 시 컴파일한다. 실패하면 순수 JS 구현인 **`bcryptjs`** 로 대체 가능 (느리지만 API는 거의 동일).

---

## 7. `express.json()` — body 파싱

해싱과는 별개지만 M1에서 처음 필요해진다.

Express는 **요청 body를 기본적으로 파싱하지 않는다.** body는 스트림으로 오는데 Express가 자동으로 읽어주지 않는다.

```js
app.use(express.json());
```

**등록하지 않으면 `req.body`가 `undefined`다.** M1에서 가장 흔한 막힘 포인트.

> 미들웨어는 등록 순서대로 실행되므로 **라우트보다 위에** 둬야 한다.

## 8. 🔑 복습 체크리스트

- [ ] 평문 저장 ❌ — 유출 시 credential stuffing으로 **다른 서비스까지** 연쇄 피해
- [ ] 해시는 단방향 — 복호화가 아니라 **다시 해싱해서 비교**
- [ ] SHA256 ❌ 이유 1: **너무 빠름** (비밀번호 저장은 느려야 함, 비대칭이 핵심)
- [ ] SHA256 ❌ 이유 2: **레인보우 테이블** (미리 계산된 표로 즉시 조회)
- [ ] 솔트 = 유저마다 다른 랜덤값 → 레인보우 테이블 무력화 + 비번 재사용 노출 방지
- [ ] **솔트는 비밀이 아니다** — 해시와 함께 저장하는 게 정상
- [ ] bcrypt = 솔트 자동 + 느림, **cost factor로 강도 조절** (권장 10~12)
- [ ] cost +1 = 2배 느려짐 → 하드웨어 발전에 대응 가능
- [ ] bcrypt 결과 문자열에 **솔트가 포함**되어 있음 → 별도 저장 불필요
- [ ] 검증은 `bcrypt.compare()` — 직접 해싱해서 `===` 비교 ❌
- [ ] `app.use(express.json())` 없으면 `req.body`가 `undefined`

## 9. 흔한 실수 / 함정

| 함정                 | 내용                                                                                                                              |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| **72바이트 절단**    | bcrypt는 입력을 72바이트에서 자른다. 더 긴 비밀번호는 뒷부분이 무시됨. 실무에선 길이 상한을 두거나 앞단에서 한 번 해싱해서 넣는다 |
| `req.body` undefined | `app.use(express.json())` 누락, 또는 라우트보다 아래에 등록                                                                       |
| `await` 누락         | `bcrypt.hash`는 Promise 반환. 빼먹으면 `Promise { <pending> }`가 저장됨                                                           |
| 해시를 응답에 포함   | 비밀번호도 해시도 응답 body에 넣지 말 것                                                                                          |
| 솔트를 숨기려 함     | 솔트는 비밀이 아니다. bcrypt는 아예 결과에 포함시킨다                                                                             |

## 10. 참고 — bcrypt 말고는?

현재 OWASP는 신규 프로젝트에 **Argon2id**를 1순위로 권장한다 (메모리까지 많이 쓰게 만들어 GPU/ASIC 공격에 더 강함). bcrypt는 여전히 안전한 선택지이고 자료가 압도적으로 많아 학습용으로 적합하다.

핵심 개념(솔트 + 의도적 느림)은 **동일하므로**, bcrypt를 이해하면 Argon2로 갈아타는 건 API 교체 수준이다.
