# M4 — 인증 미들웨어 + 보호 라우트

> **한 줄 요약**: 미들웨어는 그냥 `(req, res, next)`를 받는 함수다. `req`/`res`는 **요청 하나당 한 번 만들어져 체인을 따라 같은 참조로 흘러가므로**, 미들웨어가 붙인 값이 뒤쪽 핸들러에서 보인다.

---

## 1. 미들웨어의 정체

```js
function 미들웨어(req, res, next) { ... }
//                          ^^^^ 인자가 하나 더 있을 뿐
```

Express는 등록된 순서대로 실행한다. 각 미들웨어는 **반드시 둘 중 하나**를 해야 한다.

| 행동          | 의미                             |
| ------------- | -------------------------------- |
| `next()` 호출 | "내 일 끝, 다음으로"             |
| 응답 전송     | "여기서 끊음, 다음은 실행 안 됨" |

```
요청 → [express.json()] → [authMiddleware] → [핸들러] → 응답
           next()             next()
                                │
                                └─ 검증 실패 시 여기서 401 응답하고 끊음
```

> ⚠️ **`next()`도 안 부르고 응답도 안 보내면 요청이 영원히 매달린다.** 타임아웃까지 클라이언트가 기다린다. 모든 분기에서 둘 중 하나는 반드시.
>
> 응답을 보낼 때 `return`을 빼먹으면 아래 코드가 계속 실행돼 `next()`까지 불린다 → `Cannot set headers after they are sent`.

---

## 2. `req`/`res`는 같은 객체가 흘러간다 (실증)

미들웨어는 `req`/`res`를 **복사하지도 감싸지도 않는다.** Express가 요청당 한 번 만들고, 그 **같은 객체의 참조**를 체인에 넘긴다.

실험: `mwA`가 배열을 만들고 `mwB`가 거기에 `push`, 핸들러에서 확인.

```
=== 미들웨어 있는 라우트 (/with) ===
요청번호: 1
req.trail: ["A가 붙임", "B도 같은 객체에 붙임"]     ← 둘 다 보인다 = 같은 객체
'trail' in req: true

=== 미들웨어 없는 라우트 (/without) ===
요청번호: 2
req.trail: null
'trail' in req: false                          ← 프로퍼티 자체가 없음

=== /with 재호출 ===
요청번호: 3
req.trail: ["A가 붙임", "B도 같은 객체에 붙임"]     ← 4개로 안 늘어남
```

### 세 가지 결론

1. **미들웨어가 안 건드리면 없는 것과 완전히 동일하다.** 그냥 통과 지점일 뿐
2. **붙인 값은 그 요청의 뒤쪽에서만 보인다.** 미들웨어를 안 끼운 라우트에는 프로퍼티 자체가 없음 (`undefined`가 아니라 부재)
3. **요청마다 새로 만들어진다.** A 유저의 `req.user`가 B 유저 요청에 남을 걱정은 없다. 응답 후 버려짐

### 이걸 알면 풀리는 것 — `express.json()`

`express.json()`도 미들웨어이고, 하는 일은 **"body를 파싱해서 `req.body`에 붙이는 것"** 이다. 위 `mwA`가 `req.trail`을 붙인 것과 같은 동작.

- 라우트보다 **아래**에 등록하면 → 핸들러가 먼저 실행되고, 그땐 아무도 안 붙였으니 `undefined`
- `Content-Type`이 안 맞으면 → "내 담당 아니네" 하고 `next()`만 부르고 지나감 → 붙여줄 사람이 없어 `undefined`

`res`도 같은 객체다. 미들웨어에서 `res.setHeader(...)`하면 핸들러의 응답에 함께 나간다.

## 3. 어디에 등록하나

```js
app.use(authMiddleware); // ① 모든 라우트
app.get("/me", authMiddleware, handler); // ② 이 라우트만
```

**M4는 ②.** ①로 하면 `/health`, `/signup`, `/login`까지 토큰을 요구한다 → 로그인하려면 토큰이 필요하고 토큰을 받으려면 로그인해야 하는 교착.

## 4. `Authorization: Bearer` — 왜 헤더인가

```
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
```

다른 선택지는 전부 토큰을 흘린다.

| 방식                 | 문제                                                                                                                |
| -------------------- | ------------------------------------------------------------------------------------------------------------------- |
| 쿼리스트링 `?token=` | **서버 액세스 로그에 URL 통째로 기록**(nginx 기본 설정). 브라우저 히스토리. **`Referer` 헤더로 외부 사이트에 전송** |
| body                 | GET엔 body가 없는 게 정상. 모든 요청에 body를 강제                                                                  |
| **헤더**             | 로그에 기본적으로 안 남고, `Referer`로 안 새고, GET에도 실림 ✅                                                     |

`Bearer`는 RFC 6750의 스킴 이름. 뜻은 **"이 토큰을 소지한 자(bearer)에게 권한을 준다"** — 소지 자체가 곧 권한이라 **유출되면 즉시 사칭당한다.** 이름 자체가 경고다.

### 추출 시 주의

```js
const authHeader = req.headers.authorization; // "Bearer eyJ..."
```

- **헤더 이름은 소문자.** Node가 정규화한다 (`Authorization` → `authorization`)
- **값은 `"Bearer "` 접두사가 붙은 문자열 통째.** 그대로 `verify`에 넣으면 `"invalid token"`
- 헤더가 없으면 `undefined` → `.startsWith()` 같은 걸 바로 부르면 터진다. **검증 전에 죽지 않게** 할 것

## 5. `jwt.verify` 실패 유형 (실측)

```
정상 토큰            ✅ 통과
만료된 토큰          ❌ TokenExpiredError  "jwt expired"
payload 위조         ❌ JsonWebTokenError  "invalid signature"
다른 시크릿으로 서명   ❌ JsonWebTokenError  "invalid signature"
형식이 깨짐          ❌ JsonWebTokenError  "invalid token"
빈 문자열            ❌ JsonWebTokenError  "jwt must be provided"
undefined           ❌ JsonWebTokenError  "jwt must be provided"
```

**예외는 두 종류뿐이다.** `TokenExpiredError`(만료)와 `JsonWebTokenError`(나머지 전부).

`error.name`으로 분기한다. **`error.message`로 분기하지 말 것** — 라이브러리 버전이 바뀌면 문구가 바뀐다. `name`이 안정적인 계약이다.

> `jsonwebtoken`은 동기 함수 + 예외 던지기로 설계됐다. 정상적으로 예상되는 실패에 예외를 쓰는 게 어색해 보이지만, **try-catch 말고는 방법이 없다.**

## 6. 에러를 어디까지 알려줄까

M2에서 "실패 이유를 구분하면 정보가 샌다"고 했지만, **만료만큼은 알려주는 게 맞다.**

1. **클라이언트가 판단해야 한다.** 만료면 refresh로 재발급(M5), 위조면 로그아웃. 구분이 없으면 모든 401에서 무조건 로그아웃시키거나 무한 재시도하게 된다
2. **만료 사실은 어차피 안 숨겨진다.** `exp`가 payload에 적혀 있어 디코딩하면 보인다. 숨겨봐야 의미 없는 정보

```
TokenExpiredError  → "토큰이 만료되었습니다"      (구분)
그 외 전부          → "유효하지 않은 토큰입니다"   (뭉뚱그림)
```

나머지를 뭉뚱그리는 이유: "서명이 틀렸다" vs "형식이 깨졌다"를 구분해주면 공격자가 위조를 시도하며 **어디까지 맞췄는지 힌트**를 얻는다.

## 7. `req.user` 주입 — 조회를 어디서 하나

| 방식                     | 장점                                                                    | 단점                                                             |
| ------------------------ | ----------------------------------------------------------------------- | ---------------------------------------------------------------- |
| A. 핸들러에서 조회       | 미들웨어가 단순                                                         | **보호 라우트마다 같은 검사 반복.** 하나라도 빠뜨리면 거기서 500 |
| **B. 미들웨어에서 조회** | 미들웨어가 **"실존하는 유저"를 보장** → 핸들러는 `req.user`를 그냥 믿음 | 매 요청 조회                                                     |

**B를 택했다.** 결과적으로 핸들러가 두 줄로 끝난다.

```js
app.get("/me", authMiddleware, (req, res) => {
  return res.status(200).json({ id: req.user.id, email: req.user.email });
});
```

### 토큰이 유효해도 유저는 없을 수 있다

```
재시작 전: 200
재시작 후: 500  TypeError: Cannot read properties of undefined
```

메모리 저장소는 재시작하면 비지만 **발급된 토큰은 15분간 유효하다.** 실서비스에서도 같은 상황이 난다 — 회원 탈퇴, 관리자의 계정 삭제, DB 장애 복구.

> **"토큰이 유효하다"와 "유저가 존재한다"는 별개다.** JWT는 서버 상태를 보지 않는다. M3의 "발급된 토큰은 취소할 수 없다"가 실제 증상으로 나타난 것.

응답은 **`401`**. `404`나 "삭제된 계정입니다"로 알리면 M2에서 막은 계정 존재 노출이 여기서 다시 샌다. **위조 토큰과 동일한 메시지**를 쓴다.

## 8. `401` vs `403`

| 코드  | 이름         | 실제 의미                                                |
| ----- | ------------ | -------------------------------------------------------- |
| `401` | Unauthorized | **"누군지 모르겠다"** — 인증(authentication) 실패        |
| `403` | Forbidden    | "누군진 알겠는데 권한이 없다" — 인가(authorization) 실패 |

`401`의 이름이 "Unauthorized"라 인가처럼 보이지만 **실제로는 인증 실패**를 뜻한다. 이름이 잘못 붙은 대표 사례.

**M4는 전부 `401`.** 토큰이 없든 위조됐든 만료됐든 "확인이 안 된" 상태다. 만료를 `403`으로 하고 싶어지지만 아니다 — 메시지로만 구분하고 코드는 `401`로 통일한다. `403`은 역할(role) 개념이 생겨야 나온다.

## 9. `try` 범위는 좁게

```js
// ❌ 넓은 try — 조회 버그가 401로 둔갑
try {
  decoded = jwt.verify(...);
  const user = Object.values(users).find(...);   // 여기 버그가 나도
  next();
} catch (error) { return res.status(401)... }    // 401로 나감

// ✅ 예외를 던질 것으로 예상되는 줄만
try {
  decoded = jwt.verify(...);
} catch (error) { ... }

const user = Object.values(users).find(...);
```

실제로 이 프로젝트에서 `decoded.sub` 대신 `decoded`로 비교한 버그가 **401로 나와서** 원인 파악이 늦어졌다. try가 좁았다면 500 + 스택 트레이스로 즉시 드러났을 것.

## 10. ⚠️ 타입이 못 잡는 버그

```js
const user = Object.values(users).find((u) => u.id === decoded); // ❌ decoded.sub 여야 함
```

`decoded`는 payload 객체 통째(`{ sub, iat, exp }`)라 `u.id`(문자열)와 비교하면 **항상 false** → 유효한 토큰인데 401.

**`checkJs`가 이걸 못 잡았다.** 시도한 것과 결과:

| 시도                                              | 결과                                      |
| ------------------------------------------------- | ----------------------------------------- |
| `types/express.d.ts`로 `req.user` 선언            | ✅ 라우트 핸들러의 `req.user` 오타는 잡힘 |
| `/** @type {import("express").RequestHandler} */` | ❌ 이 버그는 못 잡음                      |
| `let decoded` → `const decoded`                   | ❌ 못 잡음                                |

이유: `authMiddleware`는 독립 함수라 TS가 Express 핸들러인 줄 모르고, `strict: false`에서 매개변수와 `decoded`가 `any`가 된다. **`any`는 아무 검사도 받지 않는다.**

> **타입 안전망에 구멍이 있었고, 하필 버그가 그 구멍 안에서 났다.** 미들웨어는 인증 로직의 심장인데 거기가 무방비였다.

문법도 타입도 멀쩡하고 **의미만 틀린** 코드다. M1~M2의 교훈이 그대로 반복된다 — **툴이 잡는 것과 사람이 잡아야 하는 것은 다르다.** 이런 건 돌려봐야 나온다.

## 11. 🔑 복습 체크리스트

- [ ] 미들웨어 = `(req, res, next)` 받는 함수. 특별한 등록 절차 없음
- [ ] 모든 분기에서 **`next()` 또는 응답 중 하나는 반드시** (안 하면 요청이 매달림)
- [ ] 응답 시 `return` 필수 — 빼먹으면 `Cannot set headers after they are sent`
- [ ] **`req`/`res`는 요청당 한 번 생성, 같은 참조로 체인을 흐른다**
- [ ] 미들웨어가 안 건드리면 없는 것과 동일 / 붙인 값은 뒤쪽에서만 보임 / 요청마다 새로 생성
- [ ] 라우트별 등록(②)을 쓸 것 — 전역이면 `/login`까지 막혀 교착
- [ ] 토큰은 **`Authorization: Bearer`** 헤더. 쿼리스트링은 로그·히스토리·`Referer`로 샌다
- [ ] `req.headers.authorization`은 **소문자**, 값에 `"Bearer "` 접두사 포함
- [ ] `jwt.verify` 실패는 **`TokenExpiredError` / `JsonWebTokenError` 두 종류**. `error.name`으로 분기 (`message` ❌)
- [ ] 만료만 구분해 알리고 **나머지는 뭉뚱그림**
- [ ] **토큰 유효 ≠ 유저 존재.** 조회 결과가 없으면 `401` (위조와 동일 메시지)
- [ ] 조회는 **미들웨어에서** — 보호 라우트가 늘어도 보장이 따라온다
- [ ] 전부 `401`. `403`은 역할 개념이 생겨야 등장
- [ ] `try` 범위는 **예외를 던질 줄만**

## 12. 흔한 실수

| 실수                                               | 결과                                                                           |
| -------------------------------------------------- | ------------------------------------------------------------------------------ |
| `if (authHeader.startsWith("Bearer "))` (`!` 누락) | **조건 반전** — 정상 요청은 401, 형식 틀린 요청은 통과                         |
| 핸들러에서 `decoded` 참조                          | `decoded`는 미들웨어의 지역 변수. `req.user`로 꺼내야 함                       |
| `u.id === decoded`                                 | `decoded`는 객체 통째. `decoded.sub` 여야 함. **항상 false → 유효 토큰이 401** |
| `res.json({ user })`                               | `passwordHash` 유출 (M2와 동일한 실수)                                         |
| 만료에 `403`                                       | `403`은 인가 실패. 인증 실패는 전부 `401`                                      |
| `find` 결과를 바로 `.id`                           | 못 찾으면 `undefined` → TypeError → 500                                        |
| `try`가 너무 넓음                                  | 무관한 버그가 401로 둔갑해 디버깅이 어려워짐                                   |
