# M3 — JWT 발급

> **한 줄 요약**: JWT는 **읽을 수 없는 문자열이 아니라 고쳐 쓸 수 없는 문자열**이다. 서명이 보장하는 건 기밀성이 아니라 **위조 방지**. 그래서 payload에 뭘 넣느냐가 그대로 보안 문제가 된다.

---

## 1. 구조 — 점 두 개로 나뉜 세 조각

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9 . eyJzdWIiOiJmMDk1MjBlZi0wZTk3Ii... . CTmOlEFemVY4be39GJwsKyJkGqZcvJcit4bpiHAhH5Q
└────────── header ──────────────┘   └────────── payload ─────────┘   └─────────── signature ────────────┘
```

| 조각      | 내용                           | 만드는 법                               |
| --------- | ------------------------------ | --------------------------------------- |
| header    | `{ alg: "HS256", typ: "JWT" }` | JSON → Base64URL                        |
| payload   | `{ sub, iat, exp }`            | JSON → Base64URL                        |
| signature | 위조 방지용                    | `HMAC-SHA256("header.payload", 시크릿)` |

**JWT는 대단한 기술이 아니다.** JSON 두 개를 Base64로 인코딩하고, 이어붙인 문자열에 HMAC을 건 것. 라이브러리 없이 `node:crypto`만으로 만들 수 있다.

```js
const b64 = (obj) => Buffer.from(JSON.stringify(obj)).toString("base64url");

const headerB64 = b64({ alg: "HS256", typ: "JWT" });
const payloadB64 = b64({ sub: "f09520ef", iat: 1735000000, exp: 1735000900 });
const signature = createHmac("sha256", SECRET)
  .update(`${headerB64}.${payloadB64}`)
  .digest("base64url");

const token = `${headerB64}.${payloadB64}.${signature}`;
```

## 2. 🚨 서명은 "숨기기"가 아니다

직접 실험한 결과:

```
── 시크릿 없이 디코딩 (공격자 입장) ──
헤더   : { alg: 'HS256', typ: 'JWT' }
페이로드: { sub: 'f09520ef-0e97', email: 'a@a.com', iat: ..., exp: ... }
→ 시크릿 없이도 전부 읽힌다.
```

**Base64는 암호화가 아니라 인코딩이다.** 누구나 되돌릴 수 있다. [jwt.io](https://jwt.io)에 붙여넣으면 바로 보이고, 브라우저 개발자도구에서도 보인다.

그럼 서명이 하는 일은?

```
── payload를 위조하면? ──
원본 토큰 검증 : 통과 ✅
위조 토큰 검증 : 실패 ❌      ← sub를 "admin-user-id"로 바꿔치기한 토큰
→ 내용은 바꿀 수 있지만, 시크릿이 없으면 서명을 다시 만들 수 없다.
```

payload를 고치는 건 누구나 할 수 있다. 하지만 **고친 내용에 맞는 새 서명을 만들려면 시크릿이 필요**하고, 시크릿은 서버만 갖고 있다.

|                                | 보장하나?     |
| ------------------------------ | ------------- |
| 기밀성 (내용을 못 읽게)        | ❌ **아니오** |
| 무결성 (내용을 못 바꾸게)      | ✅ 예         |
| 인증 (서버가 발급한 게 맞는지) | ✅ 예         |

## 3. payload에 뭘 넣나

읽힌다는 걸 알았으니 결론은 하나 — **민감한 건 절대 넣지 않는다.**

```js
// ❌ 금지
{ password: "1234" }            // 말할 것도 없음
{ passwordHash: "$2b$10$..." }  // 해시도 안 됨 (오프라인 크래킹 재료)
{ ssn: "900101-1234567" }       // 개인정보
{ role: "admin", isPaid: true } // 노출 자체가 정보인 경우

// ✅ 적절
{ sub: "f09520ef-...", iat: ..., exp: ... }
```

**최소한만.** 필요한 건 "이 토큰이 누구 것인가"뿐이고, 나머지는 서버가 그 id로 조회하면 된다.

### 표준 클레임

| 클레임 | 뜻                            | 비고                  |
| ------ | ----------------------------- | --------------------- |
| `sub`  | subject — **누구의 토큰인가** | 보통 user id          |
| `iat`  | issued at — 발급 시각         | 라이브러리 자동       |
| `exp`  | expiration — 만료 시각        | **검증 시 자동 확인** |

`sub`는 **값을 바로** 넣는다. RFC 7519에 `StringOrURI` 타입으로 정의돼 있다.

```js
{
  sub: user.id;
} // ✅
{
  sub: {
    id: user.id;
  }
} // ❌ 라이브러리는 안 막지만 표준 위반
```

> `jsonwebtoken`은 `sub`의 타입을 검사하지 않아 객체도 통과시킨다. 하지만 그러면 `sub`를 쓰는 의미가 사라진다 — API 게이트웨이·로그 수집기·인증 프록시가 `sub`를 **문자열로 전제**하고 파싱하기 때문. 표준 이름은 쓰면서 표준 이점은 못 받는 어중간한 상태가 된다.

정보를 더 담아야 하면 **`sub`를 부풀리지 말고 평평하게** 추가한다.

```js
{ sub: user.id, role: "user" }  // ✅
{ sub: { id, role } }           // ❌
```

다만 `role` 같은 건 토큰에 넣으면 **권한이 바뀌어도 만료 전까진 옛 권한이 유효**해지는 문제가 생긴다. 서버가 id로 조회하는 편이 안전하다.

## 4. 만료(`exp`)와 JWT의 최대 약점

**서버는 발급한 토큰을 취소할 수 없다.** 세션이라면 서버가 들고 있는 세션을 지우면 끝이지만, JWT는 서버에 아무것도 저장하지 않는다. 검증은 "서명이 맞나 + 안 만료됐나"만 본다.

즉 **토큰이 유출되면 만료될 때까지 공격자가 그대로 쓸 수 있다.** 로그아웃을 눌러도 그 토큰 자체는 유효하다.

대응은 **수명을 짧게**. 15분짜리가 유출되면 피해 창이 15분, 30일짜리면 30일.

> 15분마다 재로그인은 쓸 수 없는 UX다. **그 딜레마를 푸는 게 M5의 refresh 토큰.**

## 5. JWT vs 세션 — 트레이드오프

|                 | 세션                   | JWT                         |
| --------------- | ---------------------- | --------------------------- |
| 상태 저장       | 서버 (메모리/Redis/DB) | **없음** (토큰 자체가 정보) |
| 검증 비용       | 요청마다 저장소 조회   | 서명 계산만                 |
| 서버 확장       | 세션 저장소 공유 필요  | **서버가 몇 대든 무관**     |
| **즉시 무효화** | ✅ 세션 삭제로 끝      | ❌ **만료 전까지 불가**     |
| 크기            | 세션 ID만 (짧음)       | payload 통째 (김)           |

JWT가 이긴 항목은 **확장성**, 진 항목은 **무효화**. 우열이 아니라 **무엇을 포기할지의 선택**이다.

실무에선 섞어 쓴다 — access는 JWT로 짧게, refresh는 서버에 저장해 무효화 가능하게. (M5)

## 6. 시크릿 관리

```js
const SECRET = "my-secret-key"; // ❌ 하드코딩 금지
```

시크릿이 유출되면 **누구나 아무 유저의 토큰을 만들 수 있다.** `sub`에 남의 id를 넣고 서명하면 그 사람으로 로그인한 것과 같다. **비밀번호 유출보다 심각하다 — 전 계정이 한 번에 뚫린다.**

깃에 올라간 시크릿은 **커밋 히스토리에 영원히 남는다.** 나중에 지워도 과거 커밋에 있고, public 레포면 봇이 몇 분 안에 긁어간다.

### Node 20.6+ 는 dotenv 불필요

```bash
node --env-file=.env index.js
```

### fail fast — 시작 시점에 검증

```js
if (!process.env.JWT_SECRET) {
  console.error("JWT_SECRET 환경변수가 없습니다.");
  process.exit(1);
}
```

없으면 서버는 **멀쩡히 뜨고 로그인 요청이 들어와야** 500으로 터진다. 헬스체크는 통과하므로 **배포 파이프라인은 "성공"이라고 보고**하고, 실제 사용자가 로그인을 시도한 순간에야 문제가 드러난다.

> **fail fast**: 잘못된 상태면 요청을 받기 전에 죽는 게 낫다. 늦게 터질수록 발견이 늦고 피해가 크다.

`process.exit(1)`이 중요하다. `exit(0)`은 "정상 종료"로 읽혀 배포가 조용히 넘어간다.

### 시크릿 길이

HMAC-SHA256은 블록 크기(64바이트)보다 긴 키를 **내부에서 한 번 해싱해 32바이트로 줄여서** 쓴다. 32~64바이트를 넘으면 추가 보안 이득이 없다. `openssl rand -base64 32` 정도면 충분.

## 7. API

```js
// 발급
const token = jwt.sign({ sub: user.id }, process.env.JWT_SECRET, {
  expiresIn: "15m",
});

// 검증 (M4)
const decoded = jwt.verify(token, process.env.JWT_SECRET); // 실패 시 throw
decoded.sub; // → user id
```

- `expiresIn`을 주면 `exp`를 자동 계산. `iat`도 자동
- `"15m"`, `"1h"`, `"7d"` 형식
- **`verify`는 서명 검증 + 만료 확인을 둘 다 한다.** 하나라도 실패하면 예외

---

## 8. 실전 함정 — 알고리즘 혼동

header의 `alg` 필드를 옛날 라이브러리들이 **그대로 믿었다.** 공격자가 `alg: "none"`으로 바꾸고 서명을 비우면 "서명 검증 안 함"으로 통과되는 사고가 있었다.

최신 `jsonwebtoken`은 기본적으로 막지만 원리는 알아둘 것:

> **토큰이 스스로 검증 방식을 정하게 하면 안 된다.** 검증 방식은 서버가 정한다.

```js
jwt.verify(token, secret, { algorithms: ["HS256"] }); // 명시하면 확실
```

## 9. 🔑 복습 체크리스트

- [ ] JWT = `header.payload.signature`, 각각 Base64URL. **암호화 아님**
- [ ] **payload는 시크릿 없이 누구나 읽는다** — jwt.io에 붙여넣으면 보임
- [ ] 서명이 보장하는 것 = **무결성 + 인증**, 기밀성 ❌
- [ ] payload에 비밀번호·해시·개인정보 금지. **최소한만**
- [ ] `sub`는 **값을 바로** (`{ sub: user.id }`), 객체로 감싸지 않음
- [ ] 추가 정보는 `sub` 안이 아니라 **평평하게 나란히**
- [ ] **서버는 발급한 토큰을 취소할 수 없다** → 수명을 짧게 (15m)
- [ ] JWT는 **확장성을 얻고 무효화를 잃는다** (세션은 반대)
- [ ] 시크릿 하드코딩 ❌ — 유출 시 전 계정 위조 가능
- [ ] `process.env.JWT_SECRET` 없으면 **시작 시점에 `process.exit(1)`** (fail fast)
- [ ] Node 20.6+ 는 `node --env-file=.env` 로 dotenv 불필요
- [ ] `verify`는 서명 + 만료를 둘 다 검사, 실패 시 throw

## 10. 흔한 실수

| 실수                   | 결과                                                 |
| ---------------------- | ---------------------------------------------------- |
| payload에 민감정보     | 그대로 노출. Base64는 암호화가 아님                  |
| `{ sub: { id } }`      | 라이브러리는 통과시키지만 표준 도구가 깨짐           |
| 시크릿 하드코딩 / 커밋 | 커밋 히스토리에 영원히 남음. 전 계정 위조            |
| 만료 없이 발급         | 유출 시 영구 유효                                    |
| 시크릿 검증 없이 기동  | 헬스체크는 통과 → 배포 성공으로 오인 → 사용자가 발견 |
| `exit(0)` 으로 종료    | 정상 종료로 읽혀 배포가 조용히 넘어감                |
| 토큰의 `alg` 를 신뢰   | `alg: none` 우회. 서버가 알고리즘을 명시할 것        |
