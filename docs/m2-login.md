# M2 — 로그인

> **한 줄 요약**: 검증은 `bcrypt.compare(평문, 저장된해시)`로 한다. 진짜 내용은 **실패를 어떻게 알릴 것인가** — 메시지·상태 코드를 통일해도 **응답 시간**으로 계정 존재 여부가 샌다.

---

## 1. 자격 검증

M1의 역방향. 저장할 때 해싱했으니, 검증할 땐 같은 방식으로 해싱해서 비교한다.

```js
const isMatch = await bcrypt.compare(입력한_평문, 저장된_passwordHash);
```

**인자 순서는 `(평문, 해시)`.** 반대로 넣으면 항상 `false`가 나온다.

`compare`가 내부에서 하는 일:

```
1. 두 번째 인자(해시 문자열)를 파싱 → 알고리즘·cost·솔트를 꺼냄
2. 꺼낸 솔트와 cost로 평문을 해싱      ← 2^cost 반복. 비용의 전부
3. 결과를 비교
```

그래서 첫 인자는 반드시 평문이어야 한다. 저장된 해시에서 솔트를 꺼내 써야 하므로 직접 해싱해서 `===` 비교하는 건 불가능하다.

---

## 2. 실패 메시지를 통일해야 하는 이유 — user enumeration

친절해 보이지만 **취약한** 코드:

```js
if (!user)
  return res.status(404).json({ error: "존재하지 않는 이메일입니다." }); // ❌
if (!isMatch) return res.status(401).json({ error: "비밀번호가 틀렸습니다." }); // ❌
```

공격자가 이메일 목록을 던져보면:

```
victim@gmail.com  → 404 "존재하지 않는 이메일"    → 가입 안 됨
target@gmail.com  → 401 "비밀번호가 틀렸습니다"   → ★ 가입돼 있음
```

비밀번호를 몰라도 **"이 사람이 이 서비스에 가입했는지"** 를 확인할 수 있다. 이것이 **user enumeration(계정 열거)**.

### 왜 위험한가

| 결과            | 설명                                                                      |
| --------------- | ------------------------------------------------------------------------- |
| 공격 대상 압축  | 수백만 이메일 중 **실존 계정만** 걸러내 무차별 대입을 집중                |
| 피싱 정교화     | "○○ 서비스 보안 경고" 메일을 **실제 가입자에게만** 발송 → 성공률 급상승   |
| 프라이버시 침해 | 서비스 성격에 따라 **가입 사실 자체가 민감 정보** (의료·데이팅·정치·채용) |

### 해결

```js
// 이메일이 없든 비밀번호가 틀렸든 → 완전히 동일한 응답
return res
  .status(401)
  .json({ error: "이메일 또는 비밀번호가 올바르지 않습니다." });
```

로그인 화면의 그 불친절한 문구는 **의도된 설계**다.

> ⚠️ **상태 코드도 통일할 것.** 메시지만 같고 404/401로 갈리면 의미가 없다. 둘 다 `401`.

## 3. 메시지를 통일해도 새는 곳 — 타이밍 공격

```js
const user = users[email];
if (!user) return res.status(401).json({ error: "..." }); // ← bcrypt 안 돌고 즉시 return

const isMatch = await bcrypt.compare(password, user.passwordHash); // ← 여기서 ~70ms
```

메시지도 상태 코드도 완벽히 같다. 그런데 **응답 시간이 다르다.**

| 케이스                 | 실행 경로                          | 시간      |
| ---------------------- | ---------------------------------- | --------- |
| 이메일 없음            | 조회 → 즉시 return                 | **~0ms**  |
| 이메일 있음, 비번 틀림 | 조회 → **bcrypt.compare** → return | **~70ms** |

bcrypt를 일부러 느리게 만든 그 느림이 **여기서 신호가 된다.** 응답이 70ms 걸렸다면 "이 계정은 존재한다"는 뜻. 이것이 **타이밍 공격(timing attack)** — 응답 내용이 아니라 **응답에 걸린 시간**에서 정보가 새는 것.

### ❌ 단일 return으로는 못 막는다

"조기 return 대신 마지막에 한 번만 return하면 되지 않나?" → **안 된다.** 실측:

```
1. 조기 return          이메일없음   0.0ms | 비번틀림  74.3ms | 차이  74.3ms  ❌
2. 마지막 단일 return    이메일없음   0.0ms | 비번틀림  67.7ms | 차이  67.7ms  ❌
3. 더미 해시            이메일없음  69.5ms | 비번틀림  68.7ms | 차이  -0.8ms  ✅
```

**시간을 결정하는 건 `return`의 위치가 아니라 실제로 실행한 연산량이다.** 출구를 통일해도, 거기 도착하기까지 한 쪽은 bcrypt를 돌았고 한 쪽은 안 돌았다.

> 단일 return이 무의미한 건 아니다. **응답 내용의 일관성**을 구조적으로 보장한다(유지보수하다 한쪽 메시지만 바꾸는 실수를 막음). 축이 다른 문제를 풀 뿐이다.
>
> | 방식        | 통일되는 것 | 타이밍 |
> | ----------- | ----------- | ------ |
> | 단일 return | 응답 내용   | ❌     |
> | 더미 해시   | 실행 시간   | ✅     |

### ❌ 빈 문자열로 compare 하는 것도 안 된다

"유저가 없을 때 `compare(password, "")` 하면 되지 않나?" → **안 된다.** 실측:

```
"" (빈 문자열)              0.0ms   결과: false      ← 일을 안 함
undefined                 0.0ms   throw: data and hash arguments required
"notahash" (아무 문자열)     0.0ms   결과: false
$2b$10$... (진짜 해시)      64.6ms  결과: false      ← 이것만 유효
```

**비싼 건 "2^cost 반복"이고, 그걸 하려면 해시 문자열 파싱이 성공해야 한다.** cost와 솔트를 모르면 몇 번 반복할지 알 수 없으므로, 파싱 실패 시 bcrypt는 반복을 **건너뛰고 즉시 `false`를 반환**한다.

> `compare`를 **호출했다** ≠ `compare`가 **비용을 치렀다**.

### ✅ 정답 — 유효한 더미 해시

```js
// 서버 시작 시 1회만 생성 (요청마다 만들면 그것 자체가 100ms)
const DUMMY_HASH = await bcrypt.hash("dummy", 10);

const user = users[email];
const targetHash = user ? user.passwordHash : DUMMY_HASH;

const isMatch = await bcrypt.compare(password, targetHash); // 항상 ~70ms

if (!user || !isMatch) {
  return res
    .status(401)
    .json({ error: "이메일 또는 비밀번호가 올바르지 않습니다." });
}
```

- **cost를 실제 유저 해시와 동일하게** (여기선 10). 12로 하면 "유저 없음"이 더 느려져 반대 방향으로 샌다
- 평문 `"dummy"` 자체는 아무 의미 없다. **시간만 쓰는 게 목적**
- `!user ||`를 남기는 이유: 누군가 비밀번호를 `"dummy"`로 설정하면 `isMatch`가 `true`가 될 수 있다. 유저가 없는데 통과되면 안 되므로 안전장치

### 이 프로젝트 실측 결과

```
비밀번호 틀림 : 중앙값 72.7ms
없는 이메일   : 중앙값 70.8ms
차이          :        1.9ms  →  구분 불가 ✅
```

> 완벽하진 않다(네트워크 지연이 더 크고, 정밀 공격은 통계적으로 수천 번 시도해야 한다). 그래도 원리를 아는 것과 모르는 것의 차이가 크다.

## 4. 응답에 담을 것

**절대 넣지 말 것: `passwordHash`.**

```js
return res.json({ user }); // ❌ user = { id, email, passwordHash } 통째로 나감
return res.json({ id: user.id, email }); // ✅ 필요한 필드만
```

해시가 유출되면 공격자가 **오프라인에서** 무차별 대입을 돌릴 수 있다. 서버를 안 거치므로 rate limit·로그·차단이 전부 무의미해진다.

---

## 5. 🔑 복습 체크리스트

- [ ] `bcrypt.compare(평문, 해시)` — **인자 순서**. 반대로 넣으면 항상 false
- [ ] 직접 해싱해서 `===` 비교 ❌ — 저장된 해시에서 솔트를 꺼내야 하므로 `compare`만 가능
- [ ] 실패 응답은 **메시지 + 상태 코드 둘 다 통일** (401)
- [ ] 구분해서 알려주면 **user enumeration** — 실존 계정만 걸러내 공격 집중 / 피싱 정교화 / 프라이버시
- [ ] 메시지를 통일해도 **응답 시간**으로 샌다 = 타이밍 공격
- [ ] **단일 return으로는 타이밍이 안 잡힌다** — 시간은 return 위치가 아니라 **연산량**이 결정
- [ ] **빈 문자열 compare도 안 잡힌다** — 파싱 실패 시 bcrypt는 반복을 건너뛴다 (0ms)
- [ ] 해결 = **유효한 더미 해시**, 서버 시작 시 1회 생성, **cost 동일하게**
- [ ] 응답에 `passwordHash` 절대 포함 금지 — 유출 시 오프라인 무차별 대입 가능

---

## 6. 흔한 실수

| 실수                             | 결과                                             |
| -------------------------------- | ------------------------------------------------ |
| `compare(해시, 해시)`            | 항상 `false` — 첫 인자는 평문이어야 함           |
| 404 / 401 로 분기                | 메시지를 통일해도 **상태 코드로** 계정 존재가 샘 |
| `compare(pw, "")` 로 시간 맞추기 | 0ms — bcrypt가 파싱 실패로 즉시 반환             |
| 요청마다 `DUMMY_HASH` 생성       | 그것 자체가 ~100ms. 반드시 모듈 최상단에서 1회   |
| 더미 해시 cost 불일치            | 반대 방향으로 타이밍이 샘                        |
| `res.json({ user })`             | `passwordHash` 통째로 유출                       |

---

## 7. 사이드 채널이라는 감각

> **응답에서 새는 정보 = 내용 + 시간.** 두 채널을 각각 막아야 한다.

"출력을 똑같이 했으니 안 샌다"가 성립하지 않는 영역이 있다. 시간·전력·캐시 같은 게 모두 정보 통로가 되며, 이를 **사이드 채널(side channel)** 이라 한다. 인증에서 실제로 마주치는 건 대부분 타이밍이다.

**핵심은 눈으로 검토하는 것만으로는 부족하다는 것.** 빈 문자열 케이스처럼 코드가 "항상 compare를 호출"하는 것처럼 보여도 실제로는 안 되는 경우가 있다. 재봐야 안다.
